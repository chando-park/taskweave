# 구현 인계와 코드 설명

승인 메모는 사용자가 무엇을 왜 어떻게 바꾸는지 이해하고 구현 방향을 판단할 수 있어야 한다. 동시에 구현자가 저장소 전체를 다시 조사하지 않고 승인 범위를 정확히 적용할 만큼 구체적이어야 한다. 형식을 위한 그래프·heading·digest보다 실제 코드와 책임 경계를 우선한다.

## 공통 설명 작성 원칙

계획 본문, 선택적 상세 문서와 코드 앞뒤 설명, 승인안 출력, 작업 도중의 진행 안내, 구현 결과 설명에 함께 적용한다. 한글로 작성하거나 짧게 줄였다는 사실만으로 이해하기 쉬운 설명이라고 판단하지 않는다.

문서에 작성·수정·승인·검증 시각을 적을 때는 [현지 시간 기록](workplan-metadata.md)을 따른다. 사용자 시간대와 실제 시스템 시각으로 초·offset까지 기록하며, 기존 이력과 외부 원문 시각은 임의로 바꾸지 않는다.

사용자에게 보내기 직전 AI가 작성한 설명과 진행 안내가 한국어인지 확인한다. 다른 에이전트의 답변·외부 도구의 외국어 설명은 한국어로 풀어 전달하며 문장 일부만 일본어·영어로 섞지 않는다. 정확한 코드·명령·식별자와 필요한 원문 인용은 유지하고, 원문 로그와 AI의 해설을 구분한다. 이를 위해 번역 도구·별도 문서 검사·테스트를 추가하지 않는다.

진행 안내는 `실제로 확인한 사실 → 현재 문제나 미확인 부분 → 다음에 할 행동과 이유 → 코드·기록·검증 결과에 미치는 영향`을 필요한 만큼 짧게 설명한다. 문제가 없으면 없다고 밝히고, 매번 네 항목의 제목이나 고정 양식을 만들지는 않는다. 추측은 확인한 사실과 구분한다. `복구`, `정리`, `재실행`, `기준 반영`만 쓰지 말고 무엇을 중단·변경·저장·다시 실행하는지와 기존 코드·기록을 보존하는지 밝힌다. 테스트의 성공 메시지·결과 파일 저장 완료·원본과의 화면 일치 확인은 서로 대신하지 않으며 실제 확인한 범위만 말한다. 이 안내를 위해 새 조사·검사·보고서를 추가하지 않는다.

- 먼저 `언제 → 누가 → 무엇을 확인하고 → 어떻게 처리하며 → 어떤 결과가 나오는지`를 쉬운 한글로 설명한다. 현재의 문제와 변경 후의 차이를 이 순서에 연결하며, 역할 설명 없이 타입·함수 이름부터 나열하지 않는다.
- 정상 처리뿐 아니라 이번 변경에 해당하는 실패·보류·취소 때 누가 무엇을 남기고 다음에 어떻게 처리하는지도 설명한다. 호출 화살표나 상태 이름만 나열해 실제 처리 과정을 대신하지 않는다.
- 정확한 코드·API·설정 이름은 설명 뒤 괄호나 코드 블록으로 연결하고 원래 표기를 유지한다. 약어·영문 용어·함축된 명사로 동작 설명을 대신하지 않는다. 필요한 용어는 처음 등장할 때 뜻을 풀어 쓰며, 새 용어집이나 영문 단어의 일괄 번역을 요구하지 않는다.
- `금지`, `대기`, `정리`, `소유` 같은 표현은 대상과 이유를 밝힌다. 검사라면 무엇이 어느 코드를 검사하고 실패하면 어떻게 되는지, 비동기 작업이라면 누가 시작·취소하고 언제 끝났다고 판단하는지 필요한 범위에서 풀어 쓴다.
- 상세 코드도 코드만 붙이거나 식별자를 문장으로 반복하지 않는다. 코드 앞에는 목적을, 코드 뒤에는 주요 조건·인자가 필요한 이유·다음 호출·유지할 동작을 설명한다. 추상적인 설명이 남으면 해당 작업의 실제 입력·사용 상황 한 가지로 보완하되 확인하지 않은 동작을 만들지 않는다.
- 첫머리는 사용자가 이해하고 판단할 동작과 변경 이유로 시작한다. 경로·버전·해시·도구 조회·승인 조사 기록을 한 문단에 몰아넣지 말고 관련 근거 위치로 옮긴다. 기존 메타데이터나 출처를 삭제하거나 미확인 사실을 숨기라는 뜻은 아니다.
- 기술적인 근거와 현재/제안 코드는 유지한다. 쉽게 쓰기 위해 서로 다른 취소·종료 동작을 합치거나 중요한 조건을 생략하지 않는다. 긴 코드가 상세 문서에 있어도 본문과 승인 응답에는 사용자가 방향을 판단할 설명과 대표 코드를 남긴다.

예를 들어 `화면의 저수준 접근 금지`만 쓰지 않는다. 실제 설계가 그러하다면 `화면은 작업 UseCase에 실행을 요청합니다. 화면이 SDK를 직접 호출하면 작업 처리와 연결 관리가 섞이므로, 빌드 검사가 해당 호출의 파일·줄을 알려 주고 빌드를 실패시킵니다`처럼 주체·이유·검사 결과를 설명한다. 이 예시는 특정 아키텍처나 빌드 검사 도입을 요구하지 않는다.

`eligible 항목을 durable queue에 enqueue`처럼 압축하지 않는다. 실제 동작이 그러하다면 `앱은 전송 조건에 맞는 미전송 데이터를 찾습니다. 앱이 종료되어도 요청이 남도록 전송 대기 목록에 저장합니다`라고 설명한 뒤 정확한 함수와 저장 방식을 연결한다. 이 예시를 새 데이터 정책이나 구현 요구사항으로 옮기지 않는다.

승인안 작성자는 승인 요청 전에 본문과 연결한 상세 코드 설명을 함께 읽고, 사용자가 **무엇이 왜 바뀌며 누가 어떤 순서로 실행하고 어떻게 확인할지** 답할 수 있는지 확인한다. 설명이 부족하면 원문을 바로 고친다. 문서 형식 검사 통과나 출력 프로그램의 문장 조립을 설명 품질 확인으로 대신하지 않는다. 별도 검토 agent·승인 단계·검사 artifact·고정 항목 수는 추가하지 않는다.

## 승인 전 설계 완료 판단

하나라도 구현자가 다시 설계해야 할 정도로 비어 있으면 승인안을 제시하지 않는다. 계획 작성자는 승인 요청 전에 **현재 코드에서 제안한 코드로 실제 처리 흐름을 따라가며**, 다음 구현자가 새 책임·상태·분기를 결정할 부분이 남았는지 확인한다. '연결한다', '관리한다', '추후 구현한다' 같은 설명만으로 해당 설계가 끝났다고 보지 않는다.

추가·교체·삭제할 타입·함수와 호출부, 서로 다른 상태·분기의 처리 방식을 제안 코드와 이유로 설명한다. 저장·삭제·중복·실패·취소·복원은 이번 변경에 해당하는 것만 결정한다. 기존 선언·소비 코드와 필요한 원천으로 성립 여부를 확인하고, 기술적으로 확인할 수 있는 빈 부분은 계획 단계에서 조사한다. 사용자만 결정할 사항은 정확히 질문하고 같은 초안에서 기다린다.

대표 코드는 반복을 줄이는 수단이지 설계 결정을 생략하는 허가가 아니다. 전체 파일을 복제하지 않되 서로 다른 동작을 '내부 구현'으로 묶어 숨기지 않는다. 이름·포맷·승인한 동작을 그대로 수행하는 지역 보조 코드는 구현 중 구체화할 수 있다. 실행 주체·상태 흐름·데이터 수명·의존성을 새로 정해야 하면 설계가 아직 끝나지 않은 것이다. 이 판단은 문서 양식·명령·자동 검사 통과 여부가 아니라 실제 코드와 설명으로 한다.

## 구현 중 문제가 발견됐을 때

승인한 설계를 적용하는 과정의 인자명·타입 사용 오류나 구현 누락은 같은 승인으로 좁게 수정·검증한다. 반면 확인된 제약 때문에 새 구조가 필요하거나 계획의 빈 설계가 드러나면 해당 경로를 중단하고 현재 코드를 보존한다. 실패 근거·계획이 성립하지 않는 이유·대안의 제안 코드·검증을 같은 Workplan에 보완해 바뀐 안의 승인을 받는다. 목표나 서버 API가 같다는 이유만으로 새 설계를 구현 세부로 취급하지 않는다.

환경 문제만으로 설계를 바꾸지 않는다. 원복이 필요하면 AI가 정확한 대상·이유·영향과 보존할 코드를 먼저 설명한다. 승인된 수정 안의 구현 오류를 고치는 것은 같은 승인으로 처리하되, 승인한 구현을 폐기하고 이전 상태로 돌아가 재설계하려면 그 원복안의 명시 승인을 받는다. 사용자·다른 작업의 변경을 일괄 되돌리거나 과거 파일 상태로 전체 초기화하지 않는다. 예기치 못한 제약의 처리는 예외이며 설계를 구현 단계로 미루는 기본 절차가 아니다.

## 승인 메모의 최소 인계

- 변경 이유와 기대 동작
- 파일·심볼과 현재 호출/삽입 지점
- 핵심 현재 코드와 제안 코드
- 함께 바뀌는 caller·consumer·assembly
- 유지할 동작, 제외 범위와 외부 계약
- 실제 확인한 API 선언·type 제약·resource accessor·test locator
- 최소 직접 검증의 변경, 실패 위험, 방법, 통과 기준

전체 파일을 복제하지 않는다. 같은 기계적 변경은 대표 코드와 대상 목록으로 묶는다. 정확한 API·삽입 지점·caller·검증을 코드와 원천에서 확정할 수 없으면 예시를 발명하지 않고 승인 준비를 멈춘다. 긴 코드만 선택적 `Details/plan-code.md`로 분리한다.

여러 데이터·상태·호출 경로가 함께 바뀌면 파일 목록만 나열하지 말고, 승인 전에 행동별 핵심 구현 코드를 보여 준다. 예를 들어 응답 DTO→도메인→상태 설치→화면 소비→제거할 기존 호출을 한 흐름으로 설명하고, 각각의 기대 동작과 직접 테스트를 연결한다. 실제 대상 언어로 작성하며 확인된 현재 코드와 제안 코드를 구분한다. 제안 코드는 구현 방향을 판단할 만큼 구체적으로 쓰되 완성 파일 전체나 확정되지 않은 필드를 꾸며 쓰지 않는다. 한 줄 수정은 기존 대표 before/after로 충분하며 모든 계획에 같은 소제목·항목 수를 강제하지 않는다.

버그는 증상·trigger·원인 코드, 수정 후 코드, 영향 caller, 유지할 정상 동작과 수정 전 실패/수정 후 통과할 직접 회귀 테스트를 연결한다. 기능은 public type/API 또는 이유 있는 N/A, 핵심 state/action/branch, caller/assembly와 직접 테스트를 연결한다. UI는 영향 state·interaction·navigation·geometry·Preview·Snapshot과 원본 state를 필요한 범위만 연결한다.

## 부족한 입력을 묻고 재개하기

승인안을 완성하는 데 필요한 정보가 없으면 먼저 종류를 구분한다. 코드·테스트·접근 가능한 문서에서 확인할 책임 경계나 파일 위치는 직접 조사하고 사용자에게 확인시키지 않는다. 접근할 수 없는 디자인·기획 원본, 충돌하는 제품 정책, 사용자만 결정할 수 있는 동작만 질문한다.

질문에는 이미 확인한 사실, 정확히 부족한 자료 또는 결정, 답을 받으면 이어갈 작업을 짧게 담는다. 선택이 필요하면 확인된 대안과 영향도 함께 보여 준다. 단순히 “승인 불가”라고 끝내거나 구현 가능 여부를 사용자에게 추측해 달라고 하지 않는다. 결과를 결정할 원문·제품 선택이 없으면 같은 draft에 미확인 부분을 남기고 그 자료만 기다린다. 답변이 오면 영향받는 경계만 다시 확인해 코드·검증안을 보강하고 승인안을 제시한다. 문서 제목·필드·설명 양식 부족은 이 원문 부족과 구분해 경고·마지막 보완으로 처리한다.

## 위임 구현 agent payload

직접 구현 경로에서는 이 인계 packet이나 별도 agent를 만들지 않는다. [Model Routing](model-routing.md)이 위임 구현 경로로 판정한 경우에만 Workplan 전문을 prompt에 복제하지 않고 다음을 전달한다.

- 목표, 승인 revision과 Workplan 절대 경로
- 위 최소 인계와 소유 파일·심볼
- 기존 사용자 변경, 유지 계약, 제외 범위와 중단 조건
- 검증 명령·식별자·예상 결과와 reusable evidence
- UI이면 실제로 읽은 Project Agent/Context의 UI rule leaf, 관련 Design System declaration·consumer·external-layout 규칙 또는 명시된 프로젝트 예외
- 실제 사용자 승인 내용·범위, 이미 처리한 기록·Jira 동기화와 역할 한계
- 반환 형식: 변경 파일, 실제 핵심 diff, 실행 결과·artifact 경로, 계획 편차와 재승인 필요 여부

위임 경로에서 선택한 모델은 [Model Routing](model-routing.md)이 반환한 agent로 실제 실행한다. 120초 안에 실제 diff·검증 진행이 없거나 미완성 결과를 반환하면 같은 agent에 반복 위임하지 않는다. 현재 작업이 직접 경로 조건을 만족하면 부모가 같은 승인 범위를 인계하고, 고위험이면 조용히 대체하지 않고 중단한다. 구현 agent는 Jira·Workplan lifecycle·Product Memory·commit·push·MR을 수행하지 않는다. 리뷰 agent에는 계획 결론을 정답으로 주지 않고 승인 범위, 실제 diff와 검증 근거만 제공한다.

## 구현 결과 설명

코드와 설계 컨셉을 자세히 설명하는 주 시점은 구현 후가 아니라 **구현 전에 계획을 승인받을 때**다. AI가 다음 내용을 사용자에게 직접 설명한다. 문서 validator의 출력·성공이나 별도 승인 stamp는 이 설명과 실제 사용자 승인을 대신하지 않으며 새 CDPower 구현의 선행 조건도 아니다.

- 변경 목적과 설계 컨셉
- 대표 현재 코드와 제안 코드
- 여러 경로를 바꾸는 경우 행동별 핵심 코드 흐름과 제거할 기존 경로
- 바뀌는 caller·assembly와 유지할 동작
- 검증 방법과 통과 기준

사용자는 이 내용을 보고 구현 방향을 승인한다. Workplan 링크만 제시하거나 파일 목록만 나열하는 것으로 대신하지 않는다.

구현 뒤에는 계획 전문을 반복하지 않되 실제 바뀐 코드를 생략하지 않는다. 호스트 도구 또는 `record_save`로 남기는 현재 결과 기록과 최종 답변에는 [사용자 상태 보고](execution-contract.md#사용자-상태-보고)에 따라 다음을 간결하게 기록한다.

- 실제 핵심 변경 전후 코드, 변경 이유와 필요한 caller·상태·효과·조립 흐름. 새 기능은 삽입 지점과 핵심 추가 코드를 보여 준다.
- 실행한 검증, 결과와 미실행 항목
- 계획과 달라진 점 또는 미구현 항목

결과 문서 링크만 제시하거나 구현 전 결과 보고서를 만드는 것으로 이 설명을 대신하지 않는다. 레거시 Workplan은 기존 CODE/REQ/TEST mapping과 Details를 그대로 사용하며 새 메모 형식으로 바꾸지 않는다.
