# 디자인 QC 조사와 수정 연결

QC 근거를 모으고 기존 작업 경로에 전달한다. 승인·구현·티켓 종료 절차를 새로 만들지 않는다.

## 대상과 원천 확인

현재 프로젝트 Agent가 명시적으로 연결한 회사 QC 지침과 관련 UI·테스트 원칙만 읽는다. 회사 지침 위치를 모르면 [공통 작업 흐름](../../references/task-workflow.md#판단에서-실제-스킬로-이어가기)의 기존 context 조회를 사용한다. 프로젝트 키·Jira 주소·상태 이름을 이 스킬에서 정하거나 다른 프로젝트 설정을 가져오지 않는다.

번호만 주어졌으면 현재 대화·프로젝트의 명시 설정으로 해석한다. 설정이 있으면 이미 알려진 접두어를 다시 묻지 않고, 사용자가 명시한 다른 키도 바꾸지 않는다. 키가 확정되지 않거나 설정이 충돌할 때만 필요한 키를 질문한다. 사용자가 지정한 티켓과 순서를 유지한다.

작업 초기에 기존 티켓 사용 여부, 기록 필요 여부와 확인할 자료를 짧게 설명한다. 지정 티켓의 본문·기대 결과·기존 댓글·첨부를 읽는다. “댓글까지 확인”은 읽기 요청이지 댓글 작성·상태 변경 권한이 아니다. 조회만 요청하면 파일·티켓을 바꾸거나 Workplan·HTML·테스트를 강제하지 않는다. 별도 구현 티켓 생성은 현재 회사 정책과 [공통 작업 흐름](../../references/task-workflow.md)의 권한을 따른다.

## 차이와 원인 조사

티켓이 연결한 디자인·기획 원천과 현재 구현·기존 정상 동작·수정 대상을 대조한다. 티켓 기대값과 원천이 충돌하면 정확한 차이를 보여 주고 질문하며 어느 쪽도 임의로 정답으로 삼지 않는다. 그 결정과 무관하게 확인 가능한 조사는 계속한다.

코드에서 확인할 원인은 [Serena 절차](../../references/serena-code-intelligence.md)와 관련 테스트로 직접 좁힌다. 증상·확인한 원인·가설·미확인을 구분하고 선언 수치가 같다는 이유로 실제 화면도 같다고 판단하지 않는다. 간격뿐 아니라 typography·줄 높이·정렬·렌더 경계를 확인한다.

접근 불가 원본·제품 판단·기기 조작처럼 외부 입력만 남으면 [부족한 입력 질문](../../references/implementation-handoff.md#부족한-입력을-묻고-재개하기)에 따라 필요한 자료·선택과 답변 뒤 이어갈 작업을 묻는다. 실행 도구의 실제 가용성과 가능한 대안을 확인하고 미실행을 통과로 바꾸지 않는다.

## 기존 경로에 인계

확인한 사실로 [공통 task-route](../../references/task-workflow.md#판단에서-실제-스킬로-이어가기)를 사용한다. 새 위험 분류·MCP·승인 schema를 만들지 않는다. 같은 요청·범위에서 이미 확정한 결과는 재사용한다.

- 조회·진단만 요청: 읽기 전용 결과와 미확인을 설명한다.
- 작고 명확한 변경안: 반환된 [/taskweave:code-change](../code-change/SKILL.md)를 실제 적용한다.
- 새 버그 수정 계획: 반환된 [/taskweave:bugfix-plan](../bugfix-plan/SKILL.md)을 실제 적용한다. 조사와 계획을 함께 요청했다면 `explicitPlanRequested: true`를 빠뜨리지 않는다.
- 현재 Workplan의 추가 제보: 반환된 [/taskweave:apply-workplan-feedback](../apply-workplan-feedback/SKILL.md)으로 같은 기록·현재 변경을 보존한다. 원인 질문도 피드백 조사와 구체적인 수정안으로 잇는다.
- 새 기능 설계가 필요함이 확인되면 공통 경로가 반환한 [/taskweave:feature-plan](../feature-plan/SKILL.md)을 따른다.

이미 읽은 QC 지침·티켓·원천·조사 코드와 현재 기록을 다음 스킬에 전달한다. 같은 근거가 있으면 QC 조사로 되돌아오거나 최초 조사를 반복하지 않는다. 계획은 티켓별 `현재 문제 → 원인 코드 → 제안 코드 → 유지 동작 → 직접 검증`을 설명한 뒤 해당 스킬의 승인을 기다린다. 승인 요청 응답 자체에도 실제 현재 코드와 제안 코드를 짝으로 보여 준다. 현재 동작을 설명한 표와 제안 코드만으로 대신하지 않는다. 긴 전문은 연결 문서로 묶되 설명 그림의 각 변경에서도 실제 파일·함수 이름과 현재/제안 코드·검증 위치로 이어져야 한다. 제목·티켓 목록과 순서는 같은 기록의 본문·뷰어·연결 설명 자료에서 일치시킨다.

## 차이에 맞는 검증과 후속 처리

[디자인 시스템 계약](../../references/design-system-implementation-contract.md)과 [UI 검증](../../references/ui-verification.md)에서 이번 차이에 필요한 확인만 선택한다.

- 정적 화면은 같은 상태·영역·환경의 독립 디자인 원천과 실제 대상 렌더를 대조한다. Snapshot 성공·빌드 성공·상수 일치를 디자인 적합성 통과로 쓰지 않는다.
- 움직임 제보는 전환 시작·중간·종료와 필요한 연속 탭·스크롤 등을 확인한다. 정지 Snapshot으로 움직임을 증명하거나 근거 없이 즉시 전환·애니메이션 제거를 해법으로 확정하지 않는다.
- Golden이 없거나 원천과 다르면 독립 원천 대조와 필요한 수정·재검증으로 잇는다. 현재 앱 렌더를 정답으로 다시 저장해 실패를 없애지 않는다.

계획·승인·구현은 반환된 기존 스킬을 따르고, 결과 설명은 [/taskweave:explain-code](../explain-code/SKILL.md)로 연결한다. 승인 뒤 새 동작이나 추가 검증안이 필요하면 [피드백 절차](../../references/acceptance-feedback-loop.md)에 따라 같은 기록에 추가 현재/제안 코드·검증안만 설명하고 승인을 기다린다. 기존 구현·원본·승인 이력을 되돌리거나 새 기록으로 대체하지 않는다.

조사·계획 완료를 제품 편집이나 Jira 시작 전환 권한으로 바꾸지 않는다. 승인된 구현의 시작은 연결된 회사 정책과 기존 apply가 담당한다. 검증 성공만으로 Jira·Workplan을 완료하지 않으며 사용자 명시 완료 요청 뒤 [/taskweave:complete-work](../complete-work/SKILL.md)로 연결한다. Git·외부 게시 권한도 추정하지 않는다.
