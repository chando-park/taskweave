# 코드 주석 원칙

새 `approval-memo-v1`의 실제 변경 설명은 구현 뒤 `Completion.md`와 사용자 보고가 소유한다. 대화 코드 승인 작업은 대화에 설명하며 문서를 강제하지 않는다. 기존 Workplan은 기존 `Details/change.md`를 유지한다. 소스 주석은 코드를 다시 읽어도 알기 어려운 의도와 제약만 보존한다.

## 주석을 남기는 경우

- 제품 정책이나 외부 시스템 제약 때문에 자연스러운 구현과 다르게 작성했다.
- BLE·펌웨어·API 동작이나 호환성 조건이 코드만으로 드러나지 않는다.
- effect 취소, 화면 수명, concurrency 순서가 깨지기 쉽다.
- 의도적인 예외·우회가 있고 제거 조건이 있다.
- 임계값·수치의 출처와 경계 의미가 필요하다.
- 이후 단순화 과정에서 깨뜨리기 쉬운 불변식이 있다.

`state.alert = nil`처럼 코드가 그대로 설명하는 동작, 함수명 반복, 변경 이력과 티켓 전문은 주석으로 쓰지 않는다. 주석은 현재 코드와 함께 검증하고 오래된 설명을 남기지 않는다.

## 언어와 형식

- 저장소의 `AGENTS.md`, lint, 기존 DocC·주석 언어 관례가 우선한다.
- 프로젝트 규칙이 허용하면 비자명한 의도와 제약은 한국어로 간결하고 구체적으로 설명한다.
- public API DocC와 외부 배포 코드의 언어는 저장소 규칙을 따른다. 개인 Runtime이 모든 회사 저장소에 한국어를 강제하지 않는다.
- 한 줄이면 충분한 내용을 형식을 맞추기 위해 세 줄로 늘리지 않는다. 복수 제약이 엮혀 있을 때만 다음 라벨 중 필요한 것을 사용한다.

```swift
// 의도: 사용자가 화면을 나가도 저장 중인 요청은 취소하지 않는다.
// 제약: 동일 ID의 중복 전송은 서버에서 멱등적으로 처리한다.
// 변경 시 확인: 재시도·취소·중복 요청 테스트를 함께 확인한다.
```

- public API는 저장소 관례에 맞는 DocC로 입력·반환·오류·side effect 계약을 설명한다. 내부 구현 순서를 풀어쓰지 않는다.
- `TODO` 주석은 담당 issue·Workplan 또는 제거 조건과 같이 남긴다. 근거 없는 “나중에 정리”는 남기지 않는다.

## 계획과 구현 연결

- 계획은 주석이 필요한 제약과 대상 심볼을 지정한다. 모든 수정 라인에 주석을 요구하지 않는다.
- 구현은 해당 심볼을 바꾸기 직전에 이 계약을 적용하고, 이름·타입·구조로 설명할 수 있는 코드에는 주석을 추가하지 않는다.
- 구현 후에는 주석이 실제 diff와 일치하는지, Markdown·Workplan의 변경 설명을 중복하는지, 이미 무효한 주석이 남았는지 확인한다.
