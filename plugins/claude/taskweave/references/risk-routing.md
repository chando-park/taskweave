# Risk Routing

작업 종류·진행 방식·기록 정책은 [공통 작업 흐름](task-workflow.md)이 소유한다. 아래는 코드·설정 변경의 위험과 기록 경계다. 요약·대본 등 비코드 요청을 기능/버그 Workplan으로 보내지 않는다. 비코드의 조직 기록 의무는 해당 문서 절차로 처리한다.

기존 기준의 실행 분기는 `task-route.mjs`가 소유하며 호출·입력은 [공통 작업 흐름의 연결](task-workflow.md#판단에서-실제-스킬로-이어가기)을 사용한다. 아래는 입력 사실을 판단하는 의미·예외다. 간단한 수정은 code-change, 의무 기록만 있는 좁은 수정은 짧은 계획 메모(direct fix), 복잡한 변경은 해당 plan 스킬로 이어간다. 질문·진단은 읽기 전용이고 고위험은 필요한 근거를 더 조사한다. 모든 변경안은 실제 코드·검증 설명 후 명시 승인을 따른다.

다음 중 하나면 code-change와 direct fix를 사용하지 않고 Workplan의 계획·승인을 거친다.

- Public API, 서버 API, BLE·펌웨어 Command/Packet 변경
- 데이터 계약·저장 형식·migration·데이터 손실 가능성
- 인증·보안·개인정보·의료 데이터 영향
- 여러 저장소 또는 앱·SDK·서버의 책임 경계 변경
- 새로운 주요 제품 정책이나 사용자 흐름 결정이 필요함
- UI source/candidate 적합성을 새로 판정하는 conformance/full 검증 또는 새 Design System 계약이 필요함

줄 수가 아니라 계약과 실패 영향으로 판단한다. 오타, 명확한 문구·spacing, 국소 guard와 그 회귀 테스트는 의무 Workplan이 없으면 보통 code-change다. UI는 원천이 확인된 기존 Golden으로 좁은 regression을 실행할 수 있을 때만 이 경로를 사용한다. 원인 불명 오류는 먼저 읽기 전용으로 조사하고, 확인한 변경이 단순하면 code-change, 복잡하거나 고위험이면 계획 후 승인으로 간다. 앱 전체 로딩처럼 여러 화면의 요청 주체·상태 처리를 재분류하는 변경은 기준이 합의되었어도 계획 후 승인 대상이다. 회사 project_agent·저장소 지침의 정식 Workplan 의무는 따르되, Workplan 의무가 Jira 생성 의무를 뜻하지는 않는다.

AI가 실제 요청·영향·필수 정책으로 경로를 판단한다. 모든 코드 수정 경로는 제시한 코드·검증안에 대한 사용자 승인을 확인한다. 저위험 여부는 조사·문서·검증의 크기를 줄이는 기준이지 승인을 생략하는 근거가 아니다. 형식·문서 hash·기술적 승인 stamp를 구현 허가로 삼지 않는다. 기존 CLI 기록은 보존하고 새 CDPower 경로에서 그 검사를 다시 강제하지 않는다.

code-change는 대화 변경안, direct/normal/high-risk는 필요한 메모·계획을 제시한 응답에서 멈추고 이후 사용자가 그 안을 명시 승인해야 구현한다. 실제 승인은 대화 또는 기존 필요 문서에 한 번 기록하며 저장 처리 때문에 같은 승인을 반복하지 않는다. 최초 구현 요청·기준 합의·plan/apply 동시 호출은 변경안 승인이 아니다. 부모가 직접 구현하는 실행 방식도 이 승인을 생략하지 않는다.

Jira는 경로와 별개로 현재 작업에 적용되는 회사 정책상 필수일 때만 생성한다. `none`·선택 사항·미확인 정책에서는 자동 생성하지 않으며, 회사 저장소·feature/bug 분류·Workplan 사용만으로 의무를 추정하지 않는다.

## 회귀 예제

| 입력 | 예상 경로 |
| --- | --- |
| 의무 Workplan 없는 오타 수정 | code-change → 대화에 변경 코드·검증 제시 → 승인 후 수정; 문서 기본 생략 |
| 기존 원천 추적 Golden이 있는 명확한 UI spacing 수정 | code-change → 대화 변경안·직접 regression 방법 제시 → 승인 후 수정 |
| 회사 정책이 Workplan을 요구하는 좁은 수정 | direct fix |
| 원인 불명의 앱 오류 | 읽기 전용 진단 뒤 단순하면 code-change, 복잡하거나 고위험이면 bugfix-plan → 승인 대기 |
| BLE·FW 계약 변경 | 고위험 조사 + 승인 |
| 위험이 낮고 명확한 개인 AI 시스템 수정 요청 | code-change → 현재/제안 문구·검증 제시 → 승인 후 변경 |
| 저위험 변경의 방향부터 요청 | 대화에서 구체적인 변경 코드·검증 설명 → 해당 안의 승인을 받으면 code-change에서 구현 |
| 모델 선택·승인 체계 등 주요 실행 정책 변경 | Workplan 계획·명시 승인 |
| 회사의 간단한 수정·티켓 선택 사항 | code-change 또는 의무 Workplan이면 direct fix. Jira 생성 없음 |
| 회사의 간단한 수정·티켓 필수 | 해당 회사 정책에 따라 티켓 생성/정확한 기존 key 연결. 기록·구현 경로는 위험으로 결정 |
| 앱 전체의 여러 요청·로딩 상태 통일 | feature-plan → 계획 제시·승인 대기 → feature-apply |
| 지정 push 대상과 현재 저장소 불일치 | 중단 |
| `/taskweave:cpm`만 호출 | cpm commit |
| 커밋 푸시만 | cpm commit-push |
