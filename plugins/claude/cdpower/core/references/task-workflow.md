# 공통 작업 흐름

이 문서는 Codex와 Claude가 함께 쓰는 작업 선택 원본이다. `Codex/Runtime`이라는 경로 이름은 적용 호스트를 제한하지 않는다. 새 작업에서 선택할 때 읽고 같은 작업의 확정된 맥락은 재사용한다.

## 서로 독립적인 세 가지 선택

1. **작업 종류**: 무엇을 만드는가. 코드, 요약, 대본, 조사 등 목적·원본·산출물·제약·확인 방법을 파악한다.
2. **진행 방식**: 간단한 코드는 대화 변경안 후 승인, 복잡한 코드는 Workplan 계획 후 승인이다. 비코드 대화 작성은 해당 작업 기준을 따른다. 매번 모드를 고르게 하지는 않는다.
3. **기록 정책**: 간단한 코드 수정은 대화 기록이 기본이다. 사용자 요청·회사/저장소의 기록 의무·대화 밖 인계 필요가 있을 때만 기존 기록을 갱신하거나 짧은 문서 하나를 만든다. 복잡한 코드 변경은 승인용 Workplan을 사용한다. 문서 생략과 승인 생략을 혼동하지 않고 Jira 의무도 별도로 확인한다.

공통 순서는 `요청 파악 → 현재 자료·기준 확인 → 변경 방향 제시 → 필요한 승인 → 수정 → 검토 → 피드백에 따라 재수정 → 최종 수용`이다. 코드·보육일지·대본에 별도 프로세스를 만들지 않고 각 단계에 필요한 자료·규칙·검토 방법만 연결한다. 간단한 수정은 같은 순서를 짧게 수행하며 매번 고정 체크리스트나 보고서를 만들지 않는다. 질문·설명·진단만 요청하면 원본을 수정하지 않는다. 대화에 수정본을 제시하는 권한과 파일 덮어쓰기·외부 게시 권한도 구분한다.

## 판단에서 실제 스킬로 이어가기

디자인 QC 티켓의 조사·수정 요청이면 /cdpower:design-qc로 현재 프로젝트가 연결한 회사 QC 지침·지정 티켓·디자인 원천을 먼저 확인한다. 이미 같은 작업에서 확인한 자료는 재사용하며 그 결과로 아래 기존 task-route를 한 번 사용해 조회·작은 변경안·새 계획·현재 피드백으로 이어간다. 이 연결은 구현 승인이나 Jira 쓰기 권한을 주지 않으며 일반 티켓 조회를 디자인 QC 수정으로 확대하지 않는다.

새 요청·정정 또는 조사로 영향 범위가 바뀌면, AI는 사용자 의도와 확인한 사실을 설치된 플러그인의 `core/scripts/task-route.mjs`에 표준 입력 JSON으로 전달한다. 개발 원본은 `20_AI/Codex/Runtime/scripts/task-route.mjs`다. 같은 요청·범위의 확정된 결과는 재사용하며 최초 조사를 반복하지 않는다. 실행 실패는 현재 기준으로 판단한 이유와 실패 사실을 밝히고 가능한 작업을 계속하며 문서 형식 검사를 대신 실행하지 않는다.

입력의 `intent`는 `inspect | diagnose | propose | plan | implement`, `kind`는 `code | writing`이다. "원인과 수정 계획을 확인해 줘"처럼 조사와 계획을 함께 요청하면 `explicitPlanRequested: true`로 전달한다. 현재 Workplan이 없어도 조사에서 끝내지 않고 계획 스킬이 필요한 확인과 변경안 제시까지 담당한다. 코드 변경안에는 확인한 `contextComplete`, `repositoryCount`, `changeKind: bug | feature`와 `recordRequired`, `explicitPlanRequested`, `complexChange`, `importantDecision`, `contractRisk`의 참/거짓을 넣는다. 위험 조건의 의미는 [위험 분류](risk-routing.md)를 사용하고 미확인을 false로 채우지 않는다. `currentWorkplan`과 `relatedFeedback`은 현재 대화가 실제로 가리키는 작업일 때만 전달한다. 필요한 맥락이 없으면 `missingContext`에 그 자료만 적는다.

`read-context`는 누락된 자료만 확인한 뒤 이어가고, `read-only`는 조사·답변만 한다. 현재 코드 Workplan의 문제 제보·원인 질문은 `intent: diagnose`, `relatedFeedback: true`로 전달하며 완료 요청도 섞였으면 `completionRequested: true`를 함께 전달한다. 이 경우 일반 진단보다 현재 피드백 경로를 먼저 선택하고 `nextAction: investigate-and-propose`에 따라 원인 조사와 구체적인 수정안까지 이어간다. 이는 편집·종료 권한을 주지 않는다. 사용자가 지정한 읽기 전용 점검(`inspect`)·무관한 진단은 그대로 유지한다. `writing-work`는 글쓰기 기준으로, 그 밖에는 반환된 `skill`의 실제 SKILL.md를 읽고 이어간다. 선택 결과를 사용자에게 필요한 한 문장으로 설명한다. 경로 선택은 승인·댓글 작성·제품 편집 권한이 아니다. “댓글까지 확인”은 기존 댓글을 읽는 요청이며, 뜻이 모호하면 필요한 질문을 하고 프로젝트/담당자 답변을 게시 승인으로 바꾸지 않는다.

회사 지침은 알려진 원문을 재사용하고 모를 때만 기존 `context_read`의 `contextSources`에서 중앙 프로젝트 지침·회사 정책 위치를 찾는다. 로컬 AGENTS가 없다는 이유로 회사 정책을 생략하지 않는다. 읽기 전용 조사에서 복잡한 변경이 드러나면 확인한 범위로 수정 경로를 다시 판단하고, 수정한다면 Workplan이 필요한 이유와 다음 스킬을 설명한다. 조사 요청을 자동 문서 작성·제품 수정 권한으로 바꾸지 않는다.

변경안 승인 요청은 [구현 인계의 설계 완료 판단](implementation-handoff.md#승인-전-설계-완료-판단)과 해당 코드 스킬의 설명을 실제로 수행한 뒤 한다. 스킬 읽기 기록·파일 목록·목표 문장만으로 설명을 대신하지 않는다. 이 연결을 위한 새 보고서·영수증·승인 단계는 만들지 않는다.

## 진행 방식과 권한

- 기능 구현·동작 변경은 간단한 수정과 Workplan 모두 [구현 전 테스트 계획 설명](verification-planning.md#구현-전-테스트-계획-설명-필수)이 필수다. 구현 방향·변경 코드를 제시하기 전에 기존 테스트의 확인 범위·빈틈과 수정·추가할 테스트·이유·통과 기준을 먼저 설명한다. 구현 결과 보고에는 실제 테스트 통과 여부를 반드시 기록하고 사용자에게 알리며, 상세는 [테스트·커버리지 기록](verification-evidence.md#테스트커버리지-기록)을 따른다.
- 간단한 코드·설정 수정: 이유·대상 파일·대표 변경 전후 코드(설정/규칙은 문구)·직접 검증 방법을 대화에 먼저 보여 주고 승인 요청으로 응답을 끝낸다. “수정해 줘”라는 최초 요청만으로 편집하지 않는다. 사용자가 제시한 변경안을 명시 승인한 뒤 해당 범위만 수정·검증한다. 승인 확인을 위한 별도 파일·hash·검사를 만들지 않는다.
- 이미 승인한 변경: 같은 변경안의 구현·검증 실패 수정·재시도는 기존 승인으로 이어간다. 새 피드백으로 제안 코드·주요 동작·검증 범위가 달라지면 추가 변경안만 먼저 보여 주고 승인을 받는다. 최초 조사·승인·문서 작성을 반복하지 않는다.
- 계획 후 수정: 사용자가 방향부터 원하거나 중요한 선택·넓은 영향·고위험 계약·필수 승인 정책이 있으면 변경 컨셉·대표 변경안·확인 방법을 먼저 제시한다. 일반 글쓰기는 대화 계획으로 충분할 수 있고, 복잡한 코드·의무 기록은 승인 Workplan을 쓴다. 승인이 필요한 응답은 승인 요청으로 끝내고 사용자가 제시한 계획 버전을 명시 승인한 뒤 수정한다. 최초 구현 요청·기준 합의·스킬 호출은 일반 Workplan 승인을 대신하지 않는다.
- 회사·저장소 의무 Workplan, Public/외부 계약·저장 형식·보안·개인정보·의료 데이터·파괴적 작업은 빠른 수정 요청이나 저장된 선호로 우회하지 않는다. 코드 위험과 기록 경계는 [위험 분류](risk-routing.md)에서 확인한다.
- Jira는 현재 작업에 적용되는 회사 정책상 필수일 때만 생성한다. 선택 사항·`none`·미확인 정책이나 회사 저장소·Workplan 사용 자체를 생성 근거로 삼지 않는다. 필수 정책이 명시 승인을 요구하면 먼저 그 승인을 받는다.
- commit·push·PR/MR, 외부 게시·삭제, Jira/Workplan 종료·지식 게시 권한은 수행 요청에서 추정하지 않는다.

문서 없는 수정에서도 기존 자료·범위 밖 사용자 변경을 보존하고 독립 기준과 대조한다. 현재 수정본 자체를 기대값으로 삼거나 실행하지 않은 검증을 통과로 보고하지 않는다. 일반 요약·대본을 대화에 작성하는 것은 코드 편집으로 분류하지 않는다.

## 작업별 필요한 문서

- 코드·설정의 변경 경로를 정할 때: [위험 분류](risk-routing.md). 저위험 수정은 `/cdpower:code-change`에서 코드·검증안을 대화로 보여 주고 승인 후 수정한다. 문서는 위 기록 필요가 있을 때만 사용한다. 복잡한 기능·버그는 해당 plan/apply 스킬과 [실행 계약](execution-contract.md)을 사용한다. semantic 조사에는 Serena, Swift·UI 편집 직전에는 해당 leaf를 적용한다.
- 요약·대본·관찰 기록 등 글쓰기를 작성/수정할 때: [글쓰기 작업](writing-work.md)을 읽는다. 전문 문서·슬라이드·문체 스킬이 제공되면 필요한 기존 스킬을 사용한다. Git·프로젝트 등록·Serena·앱 테스트를 문서 작성의 선행 조건으로 만들지 않는다.
- 검토 결과를 보고할 때: [검증 근거의 공통 검토](verification-evidence.md#공통-검토와-보고)를 읽고 실제 수행한 확인·미확인 범위를 설명한다. 코드 테스트·커버리지 상세는 해당 작업에만 적용한다.
- 현재 작업 피드백/수용: [피드백 절차](acceptance-feedback-loop.md)의 대화와 Workplan 분기를 구분한다. 현재 승인 Workplan의 이력·구현을 보존하고 모드 변경만으로 새 기록이나 최초 승인을 반복하지 않는다.

회사 작업은 알려진 조직/프로젝트 정책을 먼저 따른다. 기록이 의무인 비코드 작업에는 해당 문서 기록 절차를 사용하고 코드용 Git hash를 꾸미지 않는다. 지원되는 기록 수단이 없으면 그 요구와 대안을 설명한다.

## 스킬 실행과 기록

스킬을 읽은 AI가 호스트의 파일·터미널·서비스 도구로 수정하고 검토한다. MCP가 필요하면 [플러그인 실행 연결](plugin-runtime.md)의 `context_read`·`task_current`·`record_save`만 사용한다. MCP 승인·구현 시작·검증 실행이나 기존 CLI의 문서 형식 검사를 새 작업의 허가 조건으로 삼지 않는다.

실제 대화에서 받은 승인은 해당 계획·범위와 함께 한 번 기록한다. 제목·필드·설명 형식의 부족은 경고하고 마지막에 보완하며 같은 승인을 다시 묻지 않는다. 원문 부족, 실제 테스트 실패, 새 권한 필요, 저장 충돌은 형식 문제와 구분해 해당 부분만 처리한다. 기존 Workplan·회사 이력을 이 원칙에 맞추려고 자동 변환하거나 재승인하지 않는다.

## 처음 보는 작업과 지식

익숙하지 않은 요청도 목적·원본·산출물·제약·확인 방법으로 이번 작업의 방법을 구성한다. 부족한 정보만 묻고 필요한 기존 도구/스킬을 사용한다. 새 작업 종류라는 이유로 앱 기능 계획·새 스킬·테스트 필드·전역 규칙을 먼저 만들지 않는다.

결과물 전달과 영구 지식 반영은 별개다. 이번 방법은 먼저 현재 대화에서 사용한다. 반복성과 재사용 가치가 확인되고 사용자가 동의할 때만 스킬/규칙으로 승격한다. 일반 요약·대본 수정은 결과 전달로 끝낼 수 있다. 회사 Workplan의 지식·티켓 종료는 명시 완료 요청 뒤 `/cdpower:complete-work`가 소유한다.
