# 간단한 코드 수정

처음에는 [실행 계약](../../references/execution-contract.md)과 [위험 분류](../../references/risk-routing.md)로 이 경로가 맞는지 확인한다. 현재 경로·지침·알려진 정책을 확인하고 부족할 때만 사용 가능한 resolver로 보완한다. 회사 Project Agent가 있으면 먼저 읽으며 이미 확인한 동일 작업의 경로는 반복하지 않는다.

간단하고 명확한 저위험 단일 저장소 코드·관련 설정 변경만 처리하며 요약·대본의 만능 스킬로 넓히지 않는다. 원인·기대 결과·파일·검증이 불명확하면 먼저 읽기 전용으로 좁힌다. 여러 화면·상태·요청 경로를 함께 바꾸는 복잡한 변경, 중요한 선택, Public/서버/BLE·펌웨어/저장 형식/보안·개인정보·의료 데이터/다중 저장소/주요 제품 정책/UI conformance·full은 $taskweave:bugfix-plan 또는 $taskweave:feature-plan에서 계획을 제시하고 승인을 기다린다. 회사·저장소가 간단한 수정에도 정식 Workplan을 요구하면 실행 계약의 direct fix를 사용한다. 반복 실패는 실제 위험·불확실성을 다시 평가하며 현재 승인 Workplan은 기존 경로를 유지한다.

## 짧은 작업 문서 하나

확인된 현재 프로젝트의 `workplan_root` 또는 `workplan_directory`에 `YYYYMMDD-짧은-영문-작업명.md` 하나를 만든다. 회사 작업은 회사 관리 위치를 사용하며 제품 저장소나 설치 캐시에 기록하지 않는다. 위치가 확인되지 않으면 임의 경로를 만들지 말고 기록 위치만 확인한다. 같은 작업의 피드백은 기존 파일에 이어 쓰며 과거 Workplan을 검색하거나 같은 이름을 덮어쓰지 않는다. 저장 도구 실패는 미저장 사실을 알리고 이미 확보한 자료로 가능한 수정·검증을 계속한다.

문서에는 사용자 요청·변경 이유, 대상 파일·범위, 대표 현재/변경 후 코드 또는 설정 문구, 직접 검증 방법을 짧게 적는다. 구현 뒤 실제 변경·검증 결과·미실행 범위를 같은 문서에 갱신한다. 별도 계획·결과·Completion 문서, 승인 hash, 고정 schema는 만들지 않는다. 이 문서는 정식 Workplan이 아니며 자체 승인 절차를 만들지 않는다.

AI가 호스트 파일·터미널 도구로 구현·직접 검증한다. MCP가 필요하면 조회·현재 작업 찾기·안전한 저장만 사용한다. 기록 양식의 제목·필드·설명 부족은 경고하고 마지막에 보완하며 MCP/CLI의 승인·시작·검증 orchestration을 선행 조건으로 붙이지 않는다. 실제 원문 부족·제품 테스트 실패·무권한·저장 충돌은 [플러그인 실행 연결](../../references/plugin-runtime.md)에 따라 별도로 처리한다.

Jira는 현재 작업에 적용되는 회사 정책상 필수인 경우에만 [티켓 절차](../../references/ticket-lifecycle.md)로 생성하거나 정확한 기존 key를 연결한다. 회사 저장소, 작업 문서 작성, feature/bug 분류만으로 티켓을 만들지 않는다. `none`·선택 사항·미확인 정책에서는 자동 생성하지 않는다.

## 필요한 문서 선택

- symbol·caller 관계 조사·변경: [Serena 절차](../../references/serena-code-intelligence.md)의 semantic 사전 확인과 실제 symbol/reference 조회. 정확한 문구·설정·단일 literal은 textual 예외다.
- UI 편집: [디자인 시스템 계약](../../references/design-system-implementation-contract.md)과 [UI 검증](../../references/ui-verification.md). 실제 필수 rule leaf·component/token·외부 layout 선언을 읽고 대표 Preview를 유지한다.
- Swift 편집 직전: [Swift 코드 규칙](../../references/swift-code-conventions.md)의 간격·체인·동시성·Preview를 적용하고 최종 diff에서도 확인한다.
- Swift 테스트 작성·수정: [Swift Testing 계약](../../references/swift-testing-contract.md).
- 비자명한 의도·제약 주석 작성·수정: [주석 계약](../../references/code-comment-contract.md).
- 실제 위임 필요: [모델 라우팅](../../references/model-routing.md). 직접 경로에는 형식적인 agent를 추가하지 않는다.

## 승인·구현·검증

1. 관련 원천·현재 코드·직접 테스트로 변경 경계를 확정한다. 필요한 도구·원천이 없으면 추정한 코드를 승인안으로 만들지 않고 필요한 정보만 질문한다.
2. 대상·원하는 결과·권한이 명확한 저위험 수정 요청은 수행 권한으로 사용한다. 위 짧은 기록을 한 번 남기고 바로 구현하며 형식 보완을 기다리거나 별도 승인 질문을 반복하지 않는다. 관련 설정도 실제 변경 전후 문구를 기록한다.
3. 방향·계획만 요청했으면 읽기 전용으로 답하고 원본을 수정하지 않는다. 중요한 선택·복잡한 변경·의미 범위 확대가 확인되면 기존 구현을 보존하고 plan Skill로 전환해 계획 승인을 기다린다. 같은 범위의 기존 수행 권한은 다시 묻지 않는다.
4. 현재 대상·코드가 유지되는지 확인하고 승인 범위만 수정한다. 범위 밖 dirty 변경을 보존하며 실제 충돌·대상 변경만 중단 사유다. 저장소의 아키텍처·생성·현지화·동시성·스타일 규칙을 적용한다.
5. 승인한 직접 검증부터 실행하고 위험에 비례해 빌드·정적 검사를 추가한다. UI는 none 또는 원천이 확인된 Golden의 좁은 regression만 허용한다. 원천 대조가 새로 필요하면 Workplan 경로로 전환하며 현재 렌더를 새 Golden으로 기록해 통과시키지 않는다.
6. [테스트·커버리지 기록](../../references/verification-evidence.md#테스트커버리지-기록)을 읽고 실제 테스트별 결과·집계·커버리지 실측값 또는 `미측정 — 이유`를 같은 작업 문서에 갱신하고 사용자에게 요약한다. 별도 보고서·엄격한 문서 검사·반복 테스트를 추가하지 않는다. 실제 변경 전후 핵심 코드·이유·필요한 호출 흐름, 검증 결과·미실행 범위를 직접 설명한다.

짧은 작업 문서 외에 workplan-memo·정식 Workplan·Completion·승인 hash 파일이나 과거 작업 조회를 요구하지 않는다. 구현 권한은 commit·push·PR/MR·Jira 완료·지식 게시를 포함하지 않는다. 일반 결과 전달은 별도 완료 요청을 필수로 만들지 않으며 사용자가 완료를 요청하면 $taskweave:complete-work의 대화 종료 분기를 사용한다.

## 현재 작업의 피드백

현재 대화의 수행 권한·같은 작업 문서·실제 변경만 사용한다. 범위 안 correction은 직접 영향만 수정·재검증하고 같은 문서의 결과를 갱신한다. 중요한 범위 변경·복잡한 변경·고위험·의무 Workplan 조건이 새로 생기면 현재 구현을 보존하고 해당 계획·승인 경로로 전환한다. 피드백과 완료 표현이 함께 오면 수정·검증을 먼저 처리하고 새 완료 요청 전에는 종료·게시하지 않는다.
