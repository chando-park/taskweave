# Taskweave · 작은 MCP 실행 연결

작업 선택과 권한은 [공통 작업 흐름](task-workflow.md)이 소유한다. 스킬을 읽은 AI가 필요한 자료·규칙을 선택하고 호스트의 파일·터미널·서비스 도구로 수정·검토한다. Taskweave MCP는 승인 심사·구현 시작 허가·테스트 실행 엔진이 아니다. MCP가 필요 없는 글쓰기 등은 연결 없이 진행한다.

## 업무 도구 세 가지

| 필요 | MCP 도구 | 사용 경계 |
| --- | --- | --- |
| 필요한 지침·원문 조회 | `context_read` | 확인된 작업공간·프로젝트 또는 허용 자료 참조에서 필요한 문서만 읽는다. Git 없는 기관 양식도 가능하며 전체 자료를 무조건 읽지 않는다. |
| 현재 작업 찾기 | `task_current` | 대화의 명시 ID·호스트 현재 위치 등 알려진 단서를 쓴다. 모호하면 제한된 후보만 확인하며 과거 Workplan·Jira를 전수 검색하지 않는다. |
| 기록 저장 | `record_save` | 확인된 위치·내용·고유 요청 ID를 전달한다. 기존 기록 갱신에는 읽었던 내용의 지문을 사용해 동시 변경을 덮어쓰지 않는다. |

호스트가 붙인 실제 namespace와 도구 schema를 확인한다. 도구가 노출되지 않으면 이미 아는 자료와 허용된 호스트 도구로 가능한 일을 계속하고 조회·저장의 한계만 알린다. 설치 캐시나 서버 실행 폴더를 작업 프로젝트로 오인하지 않는다.

`workplan_prepare/approve/start/feedback/result`, `verification_select/approve/run` 같은 이전 MCP orchestration은 새 일상 경로에서 사용하지 않는다. 도구가 없다는 이유로 같은 기존 CLI gate를 다시 강제하지 않는다. `model-route`·Serena 등 작업별 유틸리티가 실제 필요한 경우에는 확인한 실행 위치를 사용하되 예전 홈 bin이나 원본 checkout의 존재를 가정하지 않는다.

## 승인·형식·저장 실패 구분

실제 대화와 적용 정책에서 필요한 승인을 확인한다. 제시한 계획·범위에 대한 사용자 승인 내용을 한 번 기록하며 AI가 스스로 승인 출처를 만들지 않는다. 기록 저장은 승인 허가가 아니므로 저장 처리 때문에 같은 승인을 다시 묻지 않는다. 중요한 범위 변경·새 외부 권한은 별도로 확인한다.

- 제목·필드·설명 양식 누락은 경고하고 가능한 내용을 저장하며 끝에 한 번 보완한다. 형식 검사 성공을 수정·직접 테스트의 선행 조건으로 만들지 않는다.
- 같은 요청 ID·같은 내용의 재시도는 앞선 결과를 확인한다. 같은 ID의 다른 내용이나 동시 변경 충돌은 해당 저장만 중단하고 최신 기록 한 건을 읽어 충돌 부분만 조정한다.
- 경로 탈출·무권한 쓰기는 차단한다. 저장 충돌·권한 거절을 무시해 호스트 도구로 기존 파일을 강제 덮어쓰지 않는다.
- MCP 연결·저장 실패는 실패 위치와 미저장 사실을 알린다. 이미 확보한 자료로 가능한 수정·검토는 계속하고 복구 후 같은 기록만 안전하게 저장한다.
- 결과를 결정할 필수 원문 부족, 실제 테스트 실패·원천 불일치는 형식 문제와 다르다. 필요한 자료를 묻거나 제품을 수정·재검토하며 통과로 바꾸지 않는다.

쓰기 지문은 동시 저장 충돌 감지용이다. 코드 구현 허가나 과거 승인 기준선 일치 조건으로 사용하지 않는다. 승인·결과 기록을 위해 중복 stamp·새 영수증·과거 기록 전체 검사를 추가하지 않는다.

## 서비스·회사·설치 경계

설치·등록·복구는 setup 스킬과 관리 CLI가 맡으며 매 작업의 업무 도구로 반복하지 않는다. 기존 연결을 확인하고 필요한 설정만 제안한다. 인증값을 기록·복사하거나 설치 완료를 실제 서비스 읽기 성공으로 보고하지 않는다.

Jira·Figma·Datadog·Serena·Xcode는 호스트가 연결한 도구를 AI가 직접 사용한다. Taskweave 서버가 다른 MCP를 자동 호출한다고 가정하지 않는다. 실제 테스트는 호스트의 Xcode·터미널 등으로 실행하고 해당 작업·현재 입력에 맞는 결과만 사용한다. 다른 작업의 성공이나 도구 연결 성공을 제품 검증으로 확대하지 않는다.

회사 기록 위치·Jira 필수 여부·지식 게시·완료 권한은 신뢰한 회사 정책과 adapter를 따른다. 회사 저장소·Workplan 생성·도구 노출 자체는 Jira 생성 근거가 아니다. 사용자 명시 완료 요청 없이 테스트 성공을 Workplan/Jira 종료로 확대하지 않는다. 회사 자료·계정·토큰을 개인 패키지에 넣지 않는다.

원본은 공유 Runtime에 유지하고 생성기가 두 호스트 패키지를 만든다. 설치 복사본을 손편집하지 않는다. 원본 수정·패키지 생성·설치 적용·새 세션 실제 확인을 구분하며 사용자 환경 설치·게시·기록 이동·삭제는 별도 권한을 확인한다. 기존 `ai-workflow` 설정·연결·Workplan ID·승인 이력은 이름 전환을 이유로 변경하지 않는다.
