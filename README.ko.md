# CDPower

[English](README.md) | **한국어**

![CDPower 검정·구리색 건전지 로고](plugins/codex/taskweave/mcp/src/viewer/public/wordmark.svg)

**AI가 무엇을 바꿀지 먼저 보고 승인하고, 작업 결과와 검증까지 같은 흐름에서 확인하는 Codex·Claude Code 플러그인입니다.**

코드 수정뿐 아니라 조사·요약·대본에도 같은 작업 흐름을 사용합니다. 다만 필요한 자료와 확인 방법은 작업에 맞게 고릅니다. 작은 코드 수정은 대화에서 변경안과 승인을 주고받고, 복잡한 변경만 Workplan이라는 작업 계획 문서를 사용합니다.

이 문서는 **CDPower 0.3.9** 패키지를 설명합니다. 기존 Taskweave의 새 표시 이름입니다. 이 저장소는 사용자가 주소를 추가하는 GitHub 플러그인 장터이며, OpenAI·Anthropic의 공식 기본 장터에 입점했다는 뜻은 아닙니다. ZIP을 내려받거나 별도 서버를 준비하지 않아도 됩니다.

[설치·초기 설정](#설치와-초기-설정) · [작업 흐름](#요청부터-완료까지-어떻게-동작하나요) · [사용 예시](#실제-사용-예시) · [뷰어](#로컬-뷰어에서-workplan-읽기) · [기록 위치](#폴더와-문서는-어떻게-연결되나요) · [업데이트](#업데이트제거문제-해결)

설치 ID `taskweave`, 스킬 접두어 `$taskweave:`·`/taskweave:`, 장터 이름과 GitHub 주소는 기존 업데이트 호환을 위해 그대로입니다. 코드와 기록 폴더를 새 이름으로 옮길 필요는 없습니다. 화면·설치 설명에는 **CDPower**를 표시합니다.

## 0.3.9에 반영한 내용

- 선택한 04번 가로형 CD 건전지 로고를 적용했습니다. C 몸통은 검정 `#191919`, D 끝부분과 양극 단자는 구리색 `#B87333`입니다. 홈페이지·파비콘·브랜드 화면·다운로드 SVG의 번개 심볼을 교체합니다.
- Codex·클로드 패키지에 같은 로고를 포함합니다. 기존 화면 배치·강조색·설정·작업 기록·다른 연동은 유지합니다.

## 이전 0.3.8에 반영한 내용

- 홈·브랜드 화면·파비콘·다운로드 로고를 CDPower의 배터리·번개 심볼로 변경합니다. 배터리는 실제 잔량이나 완료율이 아닌 브랜드 그림입니다.
- 제거 전용 스킬이 플러그인 제거와 자기 소유 연결 정리를 함께 처리합니다. 다른 설치가 쓰는 뷰어는 유지하고 마지막 설치에서만 자기 뷰어를 종료합니다.
- 기존 코드·기록·설정·Serena/Figma/Jira 연결은 보존합니다. 수정된 지침이나 확인할 수 없는 프로세스는 임의로 지우거나 종료하지 않습니다.

## 어떤 작업에 도움이 되나요?

- 막연한 “이렇게 구현하겠습니다” 대신 바꿀 코드와 확인 방법을 보고 승인하고 싶을 때
- 작업에 필요한 프로젝트 규칙·코드·원본 자료만 찾아 읽게 하고 싶을 때
- 결과에 피드백을 주면 현재 구현에서 이어가고, 처음 조사부터 반복하지 않게 하고 싶을 때
- 빌드·동작 테스트·화면 대조·미검증 범위를 구분해서 보고받고 싶을 때

코드 수정, 조사, 요약, 대본은 공통 작업 흐름을 사용하지만 같은 검증을 하지는 않습니다. 요약은 원문과 의미를 대조하고 앱 수정은 관련 코드·화면을 확인합니다. 글쓰기까지 소프트웨어 프로젝트로 만들지는 않습니다.

작업은 `요청 → 필요한 자료 확인 → 변경안 설명 → 승인 → 수행·검토 → 결과 설명 → 피드백·최종 수용` 순서로 이어집니다. 모든 작업에 문서 작성·Jira·앱 테스트를 요구하지 않습니다.

## 설치와 초기 설정

### 준비할 것

Node.js 22 이상, Ruby, Git, 사용할 호스트의 CLI가 필요합니다. 호스트 로그인은 기존 방식으로 진행합니다. MCP 의존성은 패키지에 포함되어 있어 별도 `npm install`은 필요하지 않습니다.

배포 패키지와 MCP·뷰어는 macOS의 분리된 테스트 환경에서 확인했습니다. 다른 컴퓨터의 실제 설치와 Windows·Linux 동작은 아직 검증하지 않았습니다.

### Codex 설치

```sh
codex plugin marketplace add https://github.com/chando-park/taskweave.git
codex plugin add taskweave@taskweave-marketplace
```

새 대화에서 `$taskweave:setup`을 요청합니다. 입력만으로 스킬이 선택되지 않는 클라이언트에서는 스킬 선택기에서 CDPower를 검색해 선택합니다.

### Claude Code 설치

```sh
claude plugin marketplace add https://github.com/chando-park/taskweave.git --scope user
claude plugin install taskweave@taskweave-marketplace --scope user
```

새 대화에서 `/taskweave:setup`을 요청합니다.

### 초기 설정에서는 무엇을 정하나요?

일반 대화 작업은 설정을 마치지 않아도 할 수 있습니다. 프로젝트와 기록을 관리하려면 다음 내용을 준비합니다.

1. 프로젝트들이 들어 있는 상위 폴더를 알려 줍니다. 폴더 배치가 사람마다 달라도 같은 위치를 가정하지 않습니다.
2. AI가 찾은 프로젝트 목록을 확인하고 등록할 대상을 고릅니다. 프로젝트 ID는 폴더명에서 만듭니다.
3. 초기 설정이 정해진 위치에 기록 폴더를 생성합니다. 새 기록 위치를 따로 정할 필요가 없습니다.
4. 필요한 경우에만 Serena·Figma·Jira 연결을 확인합니다. 기존 연결과 외부 기록 폴더는 그대로 사용합니다.

예를 들어 다음처럼 요청할 수 있습니다.

> 프로젝트들은 `/example/projects`에 있어요. `example-app`을 등록하고 CDPower 기본 기록 폴더를 사용해 주세요. 기존 설정과 기록은 보존하고 Figma 연결은 재사용해 주세요. Jira는 프로젝트 정책상 필수일 때만 사용해 주세요.

Codex에서는 `$taskweave:setup`, 클로드에서는 `/taskweave:setup`을 실행합니다. 확인한 프로젝트를 등록하고 `~/.local/share/ai-workflow/workspaces/personal/projects/<프로젝트>/` 아래에 `Workplans`, `ProductMemory`, `Instructions`를 만듭니다. 두 호스트는 같은 설정과 기록을 사용합니다. 이미 연결된 외부 기록 폴더는 그대로 두며 옮기거나 삭제하지 않습니다.

프로젝트 폴더 예시는 자신의 경로로 바꿉니다. 기록 폴더의 기본 위치는 위와 같고, 기존 설정에 다른 위치가 있으면 보존합니다. 다른 컴퓨터에서도 그 컴퓨터의 사용자 홈 아래에 같은 구조를 만듭니다. 같은 컴퓨터의 Codex·클로드는 기록을 함께 쓰지만, 컴퓨터 간 기록 동기화는 제공하지 않습니다.

플러그인 설치만으로 전역 `AGENTS.md`·`CLAUDE.md`가 자동 교체되지는 않습니다. 먼저 이름이 붙은 스킬을 선택해 사용하세요. 모든 대화에 기본 적용하려면 기존 지침을 보존하면서 연결하는 별도 작업이 필요합니다.

## 요청부터 완료까지 어떻게 동작하나요?

```text
사용자 요청 + 현재 프로젝트
          │
          ▼
AI가 이번 작업에 맞는 CDPower 스킬을 읽음
          │
          ▼
AI가 연결된 공통 규칙·프로젝트 지침·관련 원본을 확인
          │
          ▼
변경 코드·검증 방법 제시 → 사용자 승인
          │
          ▼
호스트 도구로 파일 수정·관련 검증 실행
          │
          ▼
실제 변경·검증 결과·미확인 범위 설명
          │
          ├─ 피드백: 현재 작업에서 이어서 수정
          └─ 최종 수용: Workplan 종료는 사용자가 요청할 때
```

예를 들어 기능 추가를 요청하면 AI는 `skills/feature-plan/SKILL.md`를 읽고, 그 문서에 연결된 설명·검증 규칙과 해당 프로젝트의 실제 코드를 확인합니다. 사용자가 변경 코드와 테스트 계획을 승인하면 `feature-apply` 절차로 편집하고 검증합니다. 구현 결과에서는 바뀐 타입·함수·분기·호출 흐름을 빠뜨리지 않고 설명합니다.

규칙 문서가 작업을 대신 실행하는 것은 아닙니다. AI가 스킬과 필요한 규칙을 읽고, Codex·클로드가 제공하는 편집기·터미널·연동 도구로 실제 작업을 합니다. CDPower MCP는 자료 조회와 기록 접근을 돕습니다.

빌드 성공은 Figma 일치를 증명하지 않습니다. 화면 적합성을 확인해야 하는 작업은 독립된 디자인 원본과 실제 구현 화면을 같은 상태·범위로 대조해야 합니다. 현재 구현 화면을 그대로 정답으로 저장하는 것은 원본 적합성 검증이 아닙니다.

구현 승인은 commit·push·MR/PR 생성·외부 게시·Jira 종료·지식 게시까지 승인한 뜻이 아닙니다. 각 작업에 필요한 권한은 따로 확인합니다. 일반 대화 결과를 받아들이는 데 정식 종료 절차를 매번 요구하지는 않습니다.

## 실제 사용 예시

아래는 실제 작업 결과가 아닌 사용 예시입니다. CDPower 절차를 확실히 선택하려면 해당 스킬을 명시합니다. Codex에서는 `$taskweave:<스킬명>`, Claude Code에서는 `/taskweave:<스킬명>` 형식입니다.

### 간단한 코드 수정

`code-change`를 선택하고 요청합니다.

> 값이 없을 때 이 라벨 함수가 오류를 내요. 편집 전에 변경 코드와 검증 방법부터 보여 주세요.

AI는 관련 파일을 확인하고 다음처럼 구체적인 변경안을 제시해야 합니다.

```javascript
// 변경 전
return value.trim();

// 변경 제안
return value?.trim() ?? "";
```

실제 코드에 이 방식이 맞는 이유와 일반 값·빈 문자열·값 없음의 확인 방법을 설명한 뒤 승인을 기다립니다. 사용자가 승인하면 그 범위만 수정하고 실제 확인 결과를 보고합니다. 이 정도 작업을 위해 Markdown 파일을 새로 만드는 것이 기본은 아닙니다.

### 여러 부분에 영향을 주는 기능 추가

`feature-plan`을 선택하고 요청합니다.

> 홈의 날짜 선택기를 기존 날짜 선택 흐름에 연결할 계획을 세워 주세요. 바꿀 파일·대표 코드·테스트를 보여 주고 아직 구현하지 마세요.

AI는 프로젝트 지침·현재 코드·관련 원본을 읽고 현재 동작과 변경 동작, 주요 코드, 제외 범위, 검증 방법을 Workplan에 정리합니다. 제품 결정이나 원본이 부족하면 추측하지 않고 필요한 질문을 합니다.

사용자가 이 계획을 승인하면 `feature-apply`로 구현합니다. UI가 포함되면 디자인 시스템 계획·구현 스킬이 같은 작업에 컴포넌트·토큰·화면 검증을 더합니다. 관련 없는 별도 프로젝트를 만드는 절차가 아닙니다.

### 버그 조사와 추가 피드백

`bugfix-plan`을 선택하고 요청합니다.

> 이 폼에서 제출 요청이 두 번 나가는 원인을 조사해 주세요. 원인 코드·변경 코드·재발을 확인할 테스트를 제시하고 아직 수정하지 마세요.

AI는 확인한 사실과 가설을 구분하고 원인·수정 코드·회귀 검증을 연결합니다. 사용자가 승인한 뒤 `bugfix-apply`로 수정합니다.

이후 “오류 경로에서는 여전히 두 번 나가요”라고 피드백하면 `apply-workplan-feedback`이 현재 구현에서 이어갑니다. 이미 승인한 변경안 안의 구현·검증 실패 수정은 최초 승인을 반복하지 않습니다. 새 피드백으로 추가 코드·검증안이 필요하면 그 추가 부분만 먼저 보여 주고 승인받습니다.

### 문서 요약이나 대본 수정

> 이 회의록을 요약해 주세요. 결정·담당자·미결 질문을 남기고 파일은 만들지 마세요.

AI는 제공된 원문과 글쓰기 지침을 사용해 대화에 요약을 제시합니다. Git 등록·앱 테스트·코드 커버리지·Workplan을 요구하지 않고 원문에 없는 사실을 만들지 않아야 합니다. 현재 패키지에는 보육일지·대본 전용 스킬이 따로 있지 않습니다. 처음 보는 글쓰기는 공통 지침과 사용자가 제공한 자료로 이번 작업 방법을 정합니다.

## 로컬 뷰어에서 Workplan 읽기

호스트가 CDPower MCP를 시작하면 뷰어를 실행하고 브라우저를 한 번 엽니다. 이미 실행 중인 뷰어는 Codex·클로드가 함께 사용하고 탭을 중복으로 열지 않습니다. 플러그인 설치 직후나 모든 대화 시작이 아니라 **MCP가 시작될 때** 동작합니다.

최근 작업·검색·상태와 읽기 좋게 변환한 MD 상세 설명, 코드 흐름 페이지, 기록된 테스트 결과를 보여 줍니다. 조회 전용이므로 계획 수정·승인·티켓 변경은 하지 않습니다. 원본 MD를 HTML로 교체하지 않고, 브라우저 안에서 읽기 좋게 보여 주기만 합니다. 이 컴퓨터에서만 접속할 수 있고 다른 프로그램이 사용하는 포트는 건드리지 않습니다. 뷰어 실행이 실패해도 MCP의 자료·기록 도구는 계속 사용할 수 있습니다. 자동 실행과 브라우저 열기를 끄려면 MCP 환경에 `TASKWEAVE_VIEWER_AUTO_OPEN=0`을 설정합니다.

### 닫은 뷰어를 다시 열려면

Codex나 클로드에 다음처럼 요청합니다.

> 실행 중인 CDPower 뷰어 주소를 확인해서 브라우저로 열어 주세요. 기록과 설정은 바꾸지 마세요.

기본 실행 주소는 `~/.local/share/ai-workflow/viewer/service.json`의 `url`에 남습니다. 설정한 관리 위치가 다르면 그 위치의 `viewer/service.json`을 확인합니다. 포트는 달라질 수 있으므로 `4317`이라고 가정하지 않습니다. 브라우저를 닫아도 뷰어 서버가 계속 실행 중일 수 있습니다.

자동 실행이 되지 않으면 CDPower MCP 연결과 기본 오류 기록 `~/.local/share/ai-workflow/viewer/service.log`를 확인합니다. 직접 실행할 때는 아래 두 경로를 실제 설치 폴더와 기록 폴더로 바꿉니다.

```sh
node "/설치된/플러그인/폴더/mcp/src/viewer/main.mjs" \
  --root "/기록/Workplans"
```

터미널에 출력된 주소를 브라우저에서 엽니다. 이 직접 실행은 별도 실행 경로이며, 해당 터미널에서 Ctrl+C를 눌러 종료합니다. 기록은 지워지지 않습니다.

## 폴더와 문서는 어떻게 연결되나요?

설치 파일, 실제 작업 대상, 오래 보관할 작업 기록을 구분합니다.

```text
GitHub: chando-park/taskweave
├── .agents/plugins/marketplace.json       Codex 장터 목록
├── .claude-plugin/marketplace.json        Claude 장터 목록
└── plugins/
    ├── codex/taskweave/                  Codex용 패키지
    └── claude/taskweave/                 Claude용 패키지
        ├── skills/                      AI가 읽는 작업 절차
        ├── references/                  필요한 공통·작업별 규칙
        ├── core/                        보조 실행 파일
        └── mcp/                         로컬 MCP 프로그램·의존성

사용자 컴퓨터
├── 호스트의 플러그인 캐시                 설치 복사본, 직접 편집하지 않음
├── /example/projects/example-app/        작업할 코드·원본 자료
├── ~/.local/share/ai-workflow/workspaces/personal/projects/example-app/
│   ├── Workplans/                       이번 작업의 계획·결과
│   ├── ProductMemory/                   설정한 경우의 재사용 지식
│   └── Instructions/                    설정한 경우의 프로젝트 지침
├── ~/.config/ai-workflow/settings.json   설정·자료 위치 색인
└── ~/.local/share/ai-workflow/           관리 상태·백업·뷰어 실행 정보
```

설치는 플러그인 파일을 준비하고, 초기 설정은 사용자가 프로젝트를 확인한 뒤 기록 폴더를 생성합니다. 사용자는 프로젝트들이 들어 있는 폴더를 선택하며 새 기록 위치를 별도로 정하지 않습니다. 기존 외부 기록은 원래 위치를 유지합니다. 공통 설정은 `~/.config/ai-workflow/settings.json`에 저장합니다. `ai-workflow`라는 경로 이름은 이전 설정과의 호환을 위해 남아 있습니다.

복잡한 작업의 Workplan이 필요한 경우에는 다음처럼 기록할 수 있습니다.

```text
<workplan_root>/
└── YYYYMMDD-short-task-name/
    ├── YYYYMMDD-short-task-name.md        이유·변경 코드·검증·승인
    ├── Completion.md                     실제 구현·결과 기록
    └── Details/plan-code.md               긴 코드 설명이 필요할 때만
```

티켓이 연결된 새 작업은 폴더와 파일명을 `YYYYMMDD-<티켓번호>-short-task-name`으로 맞춥니다. 예를 들어 사용자가 `QA-123`을 기준 티켓으로 지정했다면 그 번호를 그대로 사용합니다. 기존 문서 이름을 일괄 바꾸지는 않습니다.

Workplan은 이번 일을 기록합니다. Instructions는 해당 프로젝트에서 일하는 방법이고, Product Memory는 그 지식 시스템이 설정된 경우 검토한 재사용 지식을 보관합니다. 같은 내용을 세 군데 복사하는 구조가 아니며 작업 종료만으로 지식이 조용히 게시되지는 않습니다. 간단한 수정은 대화 기록만으로 진행할 수 있습니다.

예를 들어 앱 변경을 계획하는 AI는 선택한 스킬에서 필요한 공통 규칙 링크를 따라가고, 프로젝트 지침과 직접 관련된 코드·디자인 원본을 읽습니다. 기록이 필요한 작업일 때만 정해진 관리 위치를 사용합니다. 현재 작업을 추정하려고 무관한 옛 티켓을 뒤지는 방식은 지향하지 않습니다.

## 어떤 스킬을 선택하면 되나요?

개인 작업 스킬 16개와 setup 1개가 포함되어 있습니다. 아래 이름 앞에 Codex는 `$taskweave:`, Claude는 `/taskweave:`를 붙입니다.

| 스킬 | 언제 사용하는가 | 하는 일 |
| --- | --- | --- |
| `setup` | 프로젝트·기록·연동 설정 | 필요한 설정을 안내하고 기존 연결 재사용 |
| `code-change` | 작고 명확한 코드·설정 수정 | 변경 전후 코드·검증 제시 → 승인 대기 → 구현 |
| `explain-code` | 코드 분석·Workplan 계획·구현 결과 이해 | 실행·데이터·분기 흐름을 먼저 시각화하고 단계별 코드·이유·테스트 연결. HTML은 표시 수단 |
| `project-baseline` | 새 프로젝트 구조 이해·기능 흐름 추적 | 구조·원본 조사, 지속 사용할 기준선은 요청 시 기록 |
| `feature-plan` | 영향이 넓은 기능 계획 | 구체적인 Workplan 승인안 작성, 구현하지 않음 |
| `feature-apply` | 승인한 기능 구현 | 합의한 코드 수정과 직접 검증 결과 기록 |
| `bugfix-plan` | 복잡한 버그 원인·수정 계획 | 증상·원인·변경 코드·회귀 검증 연결 |
| `bugfix-apply` | 승인한 버그 수정 | 원인 수정과 영향 동작 확인 |
| `plan-ui-with-design-system` | 기능 계획에 UI 기준 추가 | 화면 상태·공용 컴포넌트·토큰·검증 연결 |
| `implement-ui-with-design-system` | 승인한 제품 UI 구현 | 실제 디자인 시스템 선언 사용, 영향 화면·상태 검증 |
| `plan-design-system-component` | 공용 컴포넌트 추가 계획 | 공식 디자인 원본과 라이브러리를 대조해 API·variant 제안 |
| `author-design-system-component` | 승인한 공용 컴포넌트 구현 | API·토큰·variant 구현, 소비 앱을 자동 변경하지 않음 |
| `apply-workplan-feedback` | 현재 결과에 수정 피드백 | 현재 구현에서 이어가며 교정·추가 범위·별도 작업 구분 |
| `complete-work` | 현재 Workplan의 명시 종료 요청 | 실제 결과 확인과 설정된 종료 adapter만 처리 |
| `uninstall` | CDPower 또는 이전 Taskweave 사용 중단 | 선택한 호스트의 설치·자기 연결만 정리하고 공유 뷰어·기록 보존 |
| `cpm` | Git 변경 커밋·게시 | 단독 호출은 commit, push·MR/PR은 명시 요청 시만 수행, 자동 병합 안 함 |
| `promote-codex-rule` | 반복된 교훈을 규칙으로 반영 | 적절한 규칙·스킬 변경안을 검토하고 승인 후 반영 |

실제 지침은 [설치 스킬 원문](plugins/codex/taskweave/skills/)과 [공통 reference](plugins/codex/taskweave/references/)에서 확인할 수 있습니다. 공개 패키지에는 회사 전용 Jira·지식 게시·대시보드 스킬이 포함되지 않습니다. 회사 작업에 적용하려면 신뢰한 회사 정책과 adapter를 별도로 연결해야 합니다.

## MCP와 외부 도구는 각각 무엇을 하나요?

MCP는 호스트가 도구를 호출하는 통신 규약입니다. CDPower에는 다음 세 도구를 제공하는 로컬 MCP가 포함됩니다.

| 도구 | 역할 |
| --- | --- |
| `context_read` | 등록한 작업공간·허용한 자료 참조에서 필요한 내용 읽기 |
| `task_current` | 명시한 작업 ID와 제한된 단서로 현재 작업 찾기 |
| `record_save` | 중복 요청과 동시 변경 충돌을 확인하며 기록 저장 |

이 도구가 계획을 승인하거나 앱 테스트를 실행하거나 다른 MCP 서버를 자동 호출하지는 않습니다. 파일 저장 안전 검사가 AI의 다른 호스트 도구 사용까지 모두 통제하는 것도 아닙니다.

| 연동 | 사용하는 목적 | 필요한 준비 |
| --- | --- | --- |
| Serena | 코드 심볼·호출자·구현체 조사 | 호스트 연결과 프로젝트 언어 설정 |
| Figma | 디자인·공용 컴포넌트 원본 확인 | 호스트 연결, 파일 접근 권한, 해당 프레임·컴포넌트 |
| Jira | 이슈 조회와 정책상 필요한 상태 반영 | 호스트 연결, 이슈·프로젝트 정보, 필요한 수행 권한 |
| Xcode·Android 도구 | 플랫폼별 빌드·테스트 | 실제 프로젝트 도구·대상·scheme 또는 Gradle 설정 |

기존 연결은 재사용합니다. 로그인은 호스트·제공자의 공식 기능으로 진행하고 토큰을 CDPower에 붙여 넣지 않습니다. 도구가 보이는 것·인증된 것·실제로 자료를 읽은 것은 서로 다른 확인입니다. 플랫폼 지침은 포함되지만 SDK·시뮬레이터·기기·프로젝트 빌드 환경을 플러그인이 모두 설치하거나 보장하지는 않습니다.

## 업데이트·제거·문제 해결

### 업데이트

Codex:

```sh
codex plugin marketplace upgrade taskweave-marketplace
```

이 명령은 목록을 갱신합니다. Codex의 플러그인 관리에서 CDPower 업데이트를 적용하고 설치 버전이 **0.3.9**인지 확인합니다. 실행 중인 대화까지 자동으로 바뀌었다고 판단하지 않습니다.

Claude Code:

```sh
claude plugin marketplace update taskweave-marketplace
claude plugin update taskweave@taskweave-marketplace --scope user
```

설치 버전 **0.3.9**을 확인한 뒤 새 대화에서 필요한 CDPower 스킬을 선택합니다. 플러그인 업데이트가 기존 작업 기록의 이동·재작성을 뜻하지는 않습니다. 예전에 전역 지침을 특정 버전의 캐시 폴더에 직접 연결했다면 setup에 해당 연결 확인을 요청하세요. 새 패키지 설치만으로 이전 수동 연결까지 바뀌지는 않습니다. 공개 패키지의 규칙은 업데이트로 받을 수 있지만, 자신의 회사·프로젝트 전용 규칙과 서비스 로그인은 각 컴퓨터에서 별도로 준비합니다.

### 제거 — 연결 지침과 뷰어까지 함께 정리

**권장: 플러그인을 지우기 전에 해당 호스트에서 제거 스킬을 실행합니다.**

- Codex: `$taskweave:uninstall`을 선택하고 “이 Codex의 CDPower를 제거해줘. 기록은 남겨줘.”
- Claude Code: `/taskweave:uninstall`을 실행하고 같은 요청을 전달합니다.
- 둘 다 제거하려면 “Codex와 클로드의 CDPower를 모두 제거해줘. 기록은 남겨줘.”라고 명시합니다.

AI는 정확한 설치와 장터를 먼저 확인한 뒤 공식 제거 명령을 실행합니다. 제거가 확인된 설치의 관리 블록·이전 연결만 정리하며 다른 사용자 지침은 남깁니다. 사용자가 수정한 연결·소유권이 불명확한 파일은 보존하고 위치와 이유를 알립니다. 한 호스트나 중복 설치가 남으면 공용 뷰어를 유지합니다. 마지막 설치가 사라진 때만 서비스·실행 식별자·실제 프로세스가 자기 뷰어임을 확인하고 종료합니다. PID·포트만 보고 다른 프로그램을 종료하지 않습니다.

코드·Workplans·Product Memory·프로젝트 지침의 사용자 작성 내용·설정·인증·Serena/Figma/Jira 연결은 삭제하지 않습니다. 브라우저 탭은 닫지 않습니다. 기존 대화에 읽힌 지침은 지워지지 않으므로 제거 후 새 대화를 시작합니다.

터미널에서 하려면 실제 설치 폴더를 지정합니다. 첫 명령은 미리보기이며 파일을 정리하지 않습니다.

```sh
node "/설치된/플러그인/폴더/mcp/src/installation.mjs" --client codex --uninstall
# 같은 대상의 실제 제거
node "/설치된/플러그인/폴더/mcp/src/installation.mjs" --client codex --uninstall --apply
```

클로드만 대상으로 하면 `--client claude`, 둘 다는 `--client both`를 사용합니다. 같은 호스트에 여러 장터의 설치가 있으면 미리보기에서 하나를 고른 뒤, 단일 호스트와 `--plugin-selector taskweave@taskweave-marketplace`처럼 확인한 값을 지정합니다. 다른 장터를 추측해 제거하지 않습니다.

**장터의 삭제 버튼 또는 `codex plugin remove`·`claude plugin uninstall`만 직접 실행한 경우:** 플러그인 자체는 제거되지만 추가 연결·별도 뷰어까지 정리됐다고 볼 수 없습니다. 두 호스트의 공식 hook에 플러그인 삭제 전용 이벤트가 명시되지 않아 전용 제거 경로를 사용합니다. 이미 삭제했다면 남아 있는 설치본의 제거 도구로 확인하고, 도구가 없으면 남은 지침의 정확한 연결을 확인한 뒤 정리합니다. `.codex`·`.claude` 전체나 지침 파일 전체를 지우지 마세요.

### 자주 생기는 상황

- **스킬이 보이지 않아요.** 새 대화를 열고 활성화 여부를 확인한 뒤 해당 스킬을 명시적으로 선택합니다.
- **같은 스킬이 두 개 보여요.** 이전 `taskweave@my-ai-toolbox` 설치나 홈 스킬이 함께 남아 있을 수 있습니다. 새 설치를 확인하고 이전 CDPower 항목만 선택적으로 비활성화합니다. 전체 스킬을 삭제하지 않습니다.
- **기록 위치부터 물어봐요.** 기록이 필요한 작업인지 먼저 확인합니다. 단순 요약·작은 수정 때문에 전체 프로젝트 설정을 강제하면 안 됩니다.
- **외부 서비스가 연결되지 않았어요.** 호스트에서 연결하거나 그 자료 없이 가능한 범위만 진행합니다. 확인하지 못한 내용을 성공으로 만들지 않습니다.
- **시간이나 토큰이 줄어드나요?** 불필요한 읽기와 반복 작업을 줄이는 것이 설계 목표입니다. 도구 지연·모델 행동·작업에 따라 달라지므로 절감량을 보장하지 않습니다.

## 0.3.6에 반영한 내용

Codex와 클로드 패키지를 같은 공통 규칙에서 생성합니다. 이번 배포에는 다음 내용이 포함됩니다.

- 승인 전에 변경할 코드와 역할을 구체적으로 설명합니다. 구현 중 승인한 내용 밖의 새 설계가 필요해지면 먼저 설명하고 승인을 받습니다.
- 추가·변경한 타입·함수·분기·호출 흐름 전체와 테스트 목록·실제 결과·커버리지를 설명합니다. 측정하지 못한 커버리지는 미측정으로 남깁니다. 복잡한 변경은 흐름 그림에서 실제 코드·이유·테스트로 연결합니다.
- 진행 안내도 무엇을 확인했고, 무엇이 문제이며, 다음에 무엇을 하고 코드·기록에 어떤 영향이 있는지 쉽게 설명합니다.
- 사용자가 지정한 기존 티켓 번호를 그대로 사용합니다. 구현 프로젝트의 평소 번호와 다르다는 이유로 새 티켓을 만들지 않으며 기존 티켓·문서 이름도 자동 변경하지 않습니다.
- 두 호스트가 같은 프로젝트 기록을 사용하고, CDPower MCP가 시작되면 읽기 전용 Workplan 뷰어가 자동으로 열립니다.

공개 패키지에 포함된 규칙이며 회사 전용 연결 규칙과 인증 정보는 별도로 유지합니다.

MCP는 사용자 컴퓨터에서 실행하지만 AI에게 전달한 자료에는 Codex·Claude 및 연결 서비스의 데이터 처리 정책도 적용됩니다. 로컬 MCP라는 이유로 자료가 컴퓨터 밖으로 절대 전달되지 않는다고 보장하지 않습니다.
